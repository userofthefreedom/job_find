# PRD — 채용 공고 수집·관련성 랭킹·자소서 초안 작성 도구

_작성일: 2026-06-30 | 최종 수정: 2026-08-14 (v3 재설계 반영)_

---

## 1. 배경 및 목적

취업 활동 중 매일 사람인·원티드에 새로 올라오는 채용 공고를 수동으로 확인하고, 관심 있는
공고마다 자소서를 새로 쓰는 과정은 둘 다 번거롭다. 이 도구는 조건에 맞는 공고를 모아 관련성
순으로 정렬해주고, 그중 선택한 공고에 대해 AI가 자소서 초안까지 만들어준다.

> **데이터 소스 선택 배경**: 사람인 공식 Open API는 승인 절차가 까다로워 장기간 대기가
> 필요할 수 있다. 이에 사람인 공개 검색 페이지 스크래핑과 원티드 비공식 API를 조합한다.
> 사람인 공식 API가 승인되면 스크래핑 부분을 공식 API로 교체한다.

> **v3 재설계 배경**: v1~v2는 Windows 작업 스케줄러로 매일 무인 수집하는 단순 필터링
> 스크립트였다. 2026-08-14 세션에서 "찾는 과정 발전 + 자소서 초안 작성"으로 범위를 넓히기로
> 하면서, 운영 방식 자체를 명령 기반으로 전환하고 AI 자소서 오케스트레이션 파이프라인을
> 추가했다. 설계 배경과 각 단계 결정 근거는 `docs/PLAN.md` Phase 8~13을 참고.

## 2. 사용자 (Target User)

- 로컬 Windows PC에서 Python CLI를 직접 실행하는 개인 구직자
- 특정 직무·지역·경력 조건에 맞는 공고만 모아보고, 그중 관심 있는 곳에는 자소서 초안까지
  빠르게 받아보고 싶은 사람

## 3. 목표 (Goals)

| # | 목표 |
|---|---|
| G1 | 명령 실행 시 사람인·원티드에서 신규 공고를 가져온다 |
| G2 | 사용자가 `config.ini`에 정의한 조건(키워드·지역·경력 등)에 맞는 공고만 필터링한다 |
| G3 | 조건에 맞는 공고를 `output/jobs_all.txt`에 누적 기록한다 |
| G4 | 이미 기록된 공고는 중복 추가하지 않는다 (공고 ID 기준) |
| G5 | 로컬 임베딩 모델로 "직무"와 "도메인" 관련성을 평가해 상위 `top_n`건만 남긴다 (비용 없음) |
| G6 | 시스템이 못 찾은 공고를 사용자가 URL로 직접 추가할 수 있다 |
| G7 | 사용자가 선택한 공고(최대 4개)에 대해 AI가 자소서 초안을 작성해준다. 계획·작성마다
      독립된 평가 단계를 거쳐 품질을 검증한다 |
| G8 | 자소서 작성에 쓰이는 AI provider를 Claude CLI·Codex CLI·직접 API 키 중에서 역할별로
      선택할 수 있다 |

> **폐기된 목표**: v1~v2의 "Windows 작업 스케줄러로 무인 실행"(구 G5)은 v3에서 폐기했다.
> 전 과정이 사용자 명령 기반으로 전환됐다 (배경은 위 1절 참고).

## 4. 비목표 (Non-Goals)

다음 기능은 이번 단계에서 구현하지 않는다.

- **자동 지원(실제 제출)**: 자소서 초안 작성까지가 범위이며, 실제 지원 사이트에 제출하는
  것은 여전히 비목표다. 사용자가 초안을 검토·수정한 뒤 직접 지원한다.
- 이메일·카카오톡·슬랙 등 외부 알림 발송 (로컬 알림 포함)
- 사람인·원티드 외 다른 채용 사이트(잡코리아 등) 연동
- 웹 UI / 대시보드
- 복수 검색 프로필(여러 조건을 동시에 검색)
- HuggingFace 관련성 모델의 파인튜닝 (사전학습 모델만 사용 — 라벨 데이터가 쌓이면 이후 재검토)

## 6. 기능 요구사항

### 6-1. 공고 조회 (`jobfind.py collect`)

두 소스에서 최신 공고를 수집한다.

**사람인 스크래핑**
- 공개 검색 페이지(`https://www.saramin.co.kr/zf_user/search/recruit`)를 `beautifulsoup4`로 파싱한다.
- `days=1` 파라미터로 당일 등록 공고만 필터링한다.
- 페이지네이션으로 전체 수집하며, HTTP 오류 시 1회 재시도 후 해당 소스 건너뜀.

**원티드 비공식 API**
- `https://www.wanted.co.kr/api/v4/jobs` 엔드포인트를 인증 없이 호출한다.
- 최신순 정렬로 최근 공고를 수집하며, offset 기반 페이지네이션으로 전체 수집한다.
- HTTP 오류 시 1회 재시도 후 해당 소스 건너뜀.

> 어느 한 소스가 실패해도 나머지 소스 결과는 정상 처리한다.

### 6-2. 필터 조건 (`config.ini` — 상세 매칭 규칙은 `docs/SPEC.md` 참고)

`keywords`/`locations`/`career_type`/`exp_min`/`exp_max`/`exclude_keywords`를 `[filter]`
섹션에 정의한다. 조건이 비어 있으면 해당 조건을 무시한다 (전체 허용).

### 6-3. 관련성 랭킹 (`jobfind.py evaluate`)

1차 필터를 통과한 공고를 대상으로, 로컬 임베딩 모델이 `[relevance]`의 `roles`(직무)·
`domains`(도메인)와의 코사인 유사도를 각각 계산해 합산 점수로 정렬하고, 상위 `top_n`건만
`jobs_all.txt`에 남긴다. 순위 밖 공고는 `[X]`와 달리 영구 제외되지 않는다 — 다음 수집에서
경쟁 구도가 바뀌면 다시 상위권에 들 수 있다. `roles`/`domains`가 둘 다 비어 있으면 이 단계를
건너뛴다.

### 6-4. 수동 추가 (`jobfind.py add <url>`)

사람인 공고 상세 URL 또는 원티드 공고 URL(`wanted.co.kr/wd/<id>`)을 입력하면 단건 조회 후
`jobs_all.txt`에 병합한다. 이미 있는 공고(ID 기준)는 건너뛴다.

### 6-5. 자소서 선택 및 보충 자료 (`jobfind.py select`)

`jobs_all.txt`의 공고 블록 마커를 `[자소서]`로 바꾸면(최대 4개), `select` 실행 시
`output/cover_letters/<공고ID>/materials/` 폴더가 생성된다. 사용자는 이 폴더에 공고
스크린샷(이미지)이나 `notes.md`(추가 메모)를 직접 넣어둘 수 있으며, 계획 단계에서 참고된다.
5개 이상 선택 시 경고를 출력한다.

### 6-6. 자소서 오케스트레이션 파이프라인 (`jobfind.py write`)

선택된 각 공고(최대 4개)에 대해 다음 순서로 실행한다. 각 단계는 독립된 AI provider 호출이라
이전 대화 맥락을 공유하지 않는다 (격리됨).

```
계획 수립 → 계획 평가 → (NEEDS_REVISION이면 계획 재작성) → 초안 작성 → 초안 평가
```

- 계획·작성 단계는 `profile.md`(사용자 이력)와 공고 정보를 참고한다.
- 계획 단계만 `materials/`의 이미지를 함께 참고한다 (계획 산출물이 텍스트로 흡수하므로
  이후 단계는 원본 이미지가 다시 필요하지 않음).
- 원티드 공고는 상세 API의 담당업무·자격요건·우대사항을 추가로 가져와 계획·작성·평가
  전 단계에 반영한다. 사람인 공고는 상세 본문이 자바스크립트 렌더링이라 이 보강이
  불가능한 상태다 (알려진 한계, `docs/PLAN.md` Phase 12 참고).
- 초안 평가 이후 자동 재작성 루프는 없다 — 평가 의견과 초안을 함께 사용자에게 제시하고,
  재작성이 필요하면 사용자가 다시 명령한다.
- 결과는 `output/cover_letters/<공고ID>/{plan,plan_review,draft,draft_review}.md`에 저장한다.

### 6-7. AI Provider 선택 (`config.ini [providers]`)

계획/계획평가/작성/초안평가 역할마다 아래 중 하나를 선택한다.

| Provider | 방식 | 비용 |
|---|---|---|
| `claude_cli` | `claude -p` 헤드리스 호출 | 로그인된 세션 사용 (구독/한도에 따라 다름) |
| `codex_cli` | `codex exec` 헤드리스 호출 | 로그인된 세션 사용 (실제 플래그 미검증) |
| `api:anthropic` | Anthropic Messages API 직접 호출 | 호출당 과금 |
| `api:openai` | OpenAI Chat Completions API 직접 호출 | 호출당 과금 |

### 6-8. 중복 방지

- 공고 ID에 소스 prefix를 붙여 관리한다: `saramin_XXXXX`, `wanted_XXXXX`.
- 실행 시 `jobs_all.txt`를 읽어 이미 수집된 ID는 결과에서 제외한다.
- 신규 공고만 `jobs_all.txt`에 추가한다.

### 6-9. 결과 파일 형식

파일 경로: `output/jobs_all.txt` (없으면 자동 생성, 있으면 append)

공고 1건의 형식과 마커 3종(`[ ]`/`[X]`/`[자소서]`)의 의미는 `README.md` "출력 파일 형식"과
`docs/SPEC.md`를 참고.

### 6-10. 로그

- 각 커맨드는 실행 시 콘솔에 처리 건수 요약을 출력한다.
- 예: `[2026-08-14 12:05] 조회: 85건 | X 처리: 2건 | 필터 통과: 12건 | 신규 저장: 8건`
- 오류 발생 시 오류 내용도 콘솔에 출력한다.

| 항목 | 기준 |

## 8. 데이터 흐름

```
[사람인]              [원티드]
    │ (스크래핑)            │ (API)
    ▼                        ▼
fetch_saramin_all()   fetch_wanted_all()
    └──────────┬───────────┘
               ▼
         dedup + 1차 필터(config.ini)
               ▼
        output/jobs_all.txt (collect)
               │
               ▼  evaluate
   HF 임베딩 관련성 랭킹 → 상위 top_n건만 유지
               │
               ▼  add (선택)
        수동 추가 공고 병합
               │
               ▼  select
   [자소서] 마커 스캔 → materials/ 폴더 준비
               │
               ▼  write
  공고별: 계획 → 계획평가 → (재작성) → 작성 → 초안평가
               ▼
  output/cover_letters/<공고ID>/{plan,plan_review,draft,draft_review}.md
```

## 9. 성공 기준

- `collect`~`evaluate` 실행 후 `jobs_all.txt`에 조건에 맞고 관련성 높은 순으로 정렬된 공고가
  올바른 형식으로 남는다.
- 같은 날 두 번 `collect`를 실행해도 공고가 중복 추가되지 않는다.
- `config.ini`의 조건을 바꾸면 다음 실행부터 바뀐 조건이 적용된다.
- `[자소서]`로 선택한 공고에 대해 `write` 실행 시 4개 산출물(plan/plan_review/draft/
  draft_review)이 모두 생성되고, 평가 단계가 실제로 구체적인 피드백을 낸다 (rubber-stamp
  아님 — Phase 12 실데이터 검증에서 확인됨).
- provider를 `claude_cli`에서 `api:anthropic` 등으로 바꿔도 동일한 파이프라인이 동작한다.
