# PRD — 채용 공고 수집·관련성 랭킹·자소서 초안 작성 도구

_작성일: 2026-06-30 | 최종 수정: 2026-08-18 (Phase 25: 사람인 상세 이미지 자소서 반영, OQ5 해소)_

---

## 1. 배경 및 목적

취업 활동 중 매일 사람인·원티드에 새로 올라오는 채용 공고를 수동으로 확인하고, 관심 있는
공고마다 자소서를 새로 쓰는 과정은 둘 다 번거롭다. 이 도구는 조건에 맞는 공고를 모아 관련성
순으로 정렬해주고, 그중 선택한 공고에 대해 AI가 자소서 초안까지 만들어준다.

> **데이터 소스 선택 배경**: 사람인 공식 Open API는 승인 절차가 까다로워 장기간 대기가
> 필요할 수 있다. 이에 사람인 공개 검색 페이지 스크래핑과 원티드 비공식 API를 조합한다.
> 사람인 공식 API가 승인되면 스크래핑 부분을 공식 API로 교체한다.

> **v3 재설계 배경**: v1~v2는 Windows 작업 스케줄러로 매일 무인 수집하는 단순 필터링
> 스크립트였다. 2026-08-14 세션에서 "찾는 과정 발전 + 자소서 초안 작성"으로 범위를 넓히기로
> 하면서, 운영 방식 자체를 명령 기반으로 전환하고 AI 자소서 오케스트레이션 파이프라인을
> 추가했다. 설계 배경과 각 단계 결정 근거는 `docs/history/PLAN_ARCHIVE.md` Phase 8~13을 참고.

## 2. 사용자 (Target User)

- 로컬 Windows PC에서 Python CLI를 직접 실행하는 개인 구직자
- 특정 직무·지역·경력 조건에 맞는 공고만 모아보고, 그중 관심 있는 곳에는 자소서 초안까지
  빠르게 받아보고 싶은 사람

## 3. 목표 (Goals)

| # | 목표 |
|---|---|
| G1 | 명령 실행 시 사람인·원티드·자소설닷컴에서 신규 공고를 가져온다 |
| G2 | 사용자가 `.env`에 정의한 조건(키워드·지역·경력 등)에 맞는 공고만 필터링한다 |
| G3 | 조건에 맞는 공고를 `output/jobs_all.txt`에 누적 기록한다 |
| G4 | 이미 기록된 공고는 중복 추가하지 않는다 (공고 ID 기준) |
| G5 | 로컬 임베딩 모델로 "직무"와 "도메인" 관련성을 평가해 상위 `top_n`건만 남긴다 (비용 없음) |
| G6 | 시스템이 못 찾은 공고를 사용자가 URL로 직접 추가할 수 있다 |
| G7 | 사용자가 선택한 공고(최대 4개)에 대해 AI가 자소서 초안을 작성해준다. 계획·작성마다
      독립된 평가 단계를 거쳐 품질을 검증한다 |
| G8 | 자소서 작성에 쓰이는 AI provider를 Claude CLI·직접 API 키 중에서 역할별로 선택할 수
      있다 (Codex CLI는 Phase 20에서 지원 폐기) |
| G9 | 지원 기업이 DART에 등록돼 있으면 기업 개황(대표자·설립일·시장구분·홈페이지)을 자동으로
      조회해 계획 수립에 반영한다 (선택 사항). 대부분 상장기업이지만, 일부 비상장
      공시대상법인도 DART에 등록돼 있어 함께 조회된다 — 완전히 등록되지 않은 소규모
      비상장 회사는 여전히 해당 없음 (Phase 20 실키 검증에서 확인, §10 OQ6 참고) |
| G10 | 계획 수립 단계는 (지원 provider에 한해) 회사 최근 뉴스·홈페이지를 웹 검색해 진부하지
      않은 구체적인 지원동기를 계획에 반영할 수 있다 |
| G11 | `evaluate`로 추린 공고마다 목록 페이지 요약과 실제 상세 자격요건(원티드는 텍스트,
      사람인은 이미지)을 AI로 대조해 PASS/CONCERN/UNKNOWN 판정과 근거를 남긴다. 자동으로
      제거하지 않고 사용자가 `[X]`로 최종 판단하게 한다 |
| G12 | 지원한 공고의 진행 상태(지원함/면접/합격/탈락)를 `[상태]` 마커로 기록할 수 있다.
      "탈락"은 `collect` 시 `[X]`처럼 목록에서 제거되고 영구 기록되며, 나머지 상태는
      목록에 남아 콘솔 요약에 집계된다 |
| G13 | 제목에 "공채/부문별/직군별" 등 복수 직무를 한 번에 모집한다는 신호가 있는 공고는
      `[공채후보]`로 표시한다. 자동으로 개별 직무로 분리하지는 않으며, `select` 실행 시
      해당 공고에 대해서만 `notes.md`에 실제 지원하려는 세부 직무를 적어두라고 추가로
      안내한다 |
| G14 | 자소서 계획·작성·평가 단계가 공유하는 "작성 전략" 지식(두괄식·STAR 구조·지원동기
      구체성·클리셰 회피 등)을 반영해, 단순히 "잘 써라"는 지시보다 구체적인 기준으로
      초안 품질을 끌어올린다. 전략은 공개 발행된 작성법 콘텐츠와 사용자 본인 소유 자료
      분석에서만 얻는다 — 제3자 개인의 합격 자소서 원문을 수집하지 않는다 |
| G15 | 사람인·원티드는 실제 자소서 문항(질문·글자수 제한)을 거의 제공하지 않는다는 한계를
      보완하기 위해, 자소설닷컴에서 회사별 채용 이벤트와 직무 목록, 그리고 자소서 문항
      유무(문항 유형까지 — 실제 문구는 제외)를 함께 수집한다(Phase 23). 이용약관이
      허가 없는 자동화 수집을 명시적으로 금지하고 있음을 확인했고, 사용자가 그 사실을 알고도
      진행하기로 결정했다 — 이 리스크는 사용자가 직접 감수하는 것으로 합의됐다(§6-1,
      `docs/SPEC.md` §13-4a). `.env`의 `JASOSEOL_ENABLED`(기본값 `true`)로 언제든 끌 수
      있다(Phase 24) |

> **폐기된 목표**: v1~v2의 "Windows 작업 스케줄러로 무인 실행"(구 G5)은 v3에서 폐기했다.
> 전 과정이 사용자 명령 기반으로 전환됐다 (배경은 위 1절 참고).

## 4. 비목표 (Non-Goals)

다음 기능은 이번 단계에서 구현하지 않는다.

- **자동 지원(실제 제출)**: 자소서 초안 작성까지가 범위이며, 실제 지원 사이트에 제출하는
  것은 여전히 비목표다. 사용자가 초안을 검토·수정한 뒤 직접 지원한다.
- 이메일·카카오톡·슬랙 등 외부 알림 발송 (로컬 알림 포함)
- 사람인·원티드·자소설닷컴 외 다른 채용 사이트(잡코리아 등) 연동
- 웹 UI / 대시보드
- 복수 검색 프로필(여러 조건을 동시에 검색)
- HuggingFace 관련성 모델의 파인튜닝 (사전학습 모델만 사용 — 라벨 데이터가 쌓이면 이후 재검토)

## 6. 기능 요구사항

### 6-1. 공고 조회 (`jobfind.py collect`)

세 소스에서 최신 공고를 수집한다(Phase 23부터 자소설닷컴 추가).

**사람인 스크래핑**
- 공개 검색 페이지(`https://www.saramin.co.kr/zf_user/search/recruit`)를 `beautifulsoup4`로 파싱한다.
- `days=1` 파라미터로 당일 등록 공고만 필터링한다.
- 페이지네이션으로 전체 수집하며, HTTP 오류 시 1회 재시도 후 해당 소스 건너뜀.

**원티드 비공식 API**
- `https://www.wanted.co.kr/api/v4/jobs` 엔드포인트를 인증 없이 호출한다.
- 최신순 정렬로 최근 공고를 수집하며, offset 기반 페이지네이션으로 전체 수집한다.
- HTTP 오류 시 1회 재시도 후 해당 소스 건너뜀.

**자소설닷컴 비공식 API (Phase 23)** — 실제 자소서 문항 유무를 알 수 있는 유일한 소스
- `POST /employment/calendar_list.json`(회사 단위 채용 이벤트 목록, 오늘부터 30일 범위)와
  `GET /api/v1/employment_companies/<id>`(회사별 직무 목록·자소서 문항 유형)를 인증 없이
  호출한다.
- 목록 API에는 직무명이 없어 회사마다 상세 API를 별도로 불러야 하는데, 매일 전체(월 400건
  이상)를 다시 부르면 요청량이 과도해져 **이미 `jobs_all.txt`에 있는 회사는 건너뛰고 신규
  회사만** 상세조회한다(§13-4a 상세 근거). 최초 실행은 예외적으로 그 달 전체를 상세조회하는
  일회성 비용이 있다.
- **이용약관 위반 소지를 알고 사용자가 명시적으로 진행을 선택했다** — 자소설닷컴 이용약관
  제14조가 허가 없는 자동화 수집을 명시적으로 금지하고 있음을 실제 확인 후 사용자에게
  전달했고, 그럼에도 진행하기로 결정했다(§13-4a, 2026-08-17 세션 결정).
- 근무지·경력 필드를 제공하지 않아 `filter_location`/`filter_career_type`은 이 소스에
  한해 건너뛴다(job 딕셔너리의 `source` 값으로 판별).
- 자소서 문항의 실제 문구는 API에 없다(문항 유형만 "고정질문"/"자율질문"으로 제공) — 있다는
  사실과 어느 직무인지까지만 `[자소서문항]` 줄로 표시하고, 실제 문구는 사용자가 링크를 열어
  직접 확인해야 한다.

> 세 소스 중 하나가 실패해도 나머지 소스 결과는 정상 처리한다.

### 6-2. 필터 조건 (`.env` — 상세 매칭 규칙은 `docs/SPEC.md` 참고)

`FILTER_KEYWORDS`/`FILTER_LOCATIONS`/`FILTER_CAREER_TYPE`/`FILTER_EXP_MIN`/`FILTER_EXP_MAX`/
`FILTER_EXCLUDE_KEYWORDS`/`FILTER_EXCLUDE_COMPANIES` 환경변수로 정의한다. 조건이 비어 있으면
해당 조건을 무시한다(전체 허용). `FILTER_CAREER_TYPE`은 쉼표로 여러 값을 선택할 수 있다(예:
"신입, 경력무관" — Phase 6). 경력 연차 필터(`FILTER_EXP_MIN`/`MAX`)는 공고 요구 범위와 설정
범위가 조금이라도 겹치면 통과하는 overlap 방식을 유지한다 — Phase 6에서 "설정 범위 안에
완전히 포함될 때만 통과"하는 containment 방식으로 바꾸는 안을 검토했으나, 지원 가능한
시니어 공고까지 넓게 보고 싶다는 판단으로 현재 방식을 유지하기로 확정했다.

### 6-3. 관련성 랭킹 (`jobfind.py evaluate`)

1차 필터를 통과한 공고를 대상으로, 로컬 임베딩 모델이 `RELEVANCE_ROLES`(직무)·
`RELEVANCE_DOMAINS`(도메인)와의 코사인 유사도를 각각 계산해 결합 점수로 정렬하고, 상위
`RELEVANCE_TOP_N`건만 `jobs_all.txt`에 남긴다. 둘 다 설정된 경우 두 점수를 곱해 결합한다 —
한쪽이 0에 가까우면 다른 쪽이 아무리 높아도 총점이 낮아지도록 해, 직무 쪽 문자열만 우연히
겹치고 도메인은 전혀 안 맞는 공고가 상위에 오르는 문제를 줄인다. 순위 밖 공고는 `[X]`와
달리 영구 제외되지 않는다 — 다음 수집에서 경쟁 구도가 바뀌면 다시 상위권에 들 수 있다.
`RELEVANCE_ROLES`/`RELEVANCE_DOMAINS`가 둘 다 비어 있으면 이 단계를 건너뛴다.

> **알려진 한계**: 사전학습 임베딩 모델이 짧은 공고 제목만으로 도메인을 뚜렷하게 구분하지
> 못하는 경우가 실사용 중 확인됐다 — 예를 들어 "IT/웹/앱" 도메인 점수가 사무행정 공고와
> 실제 IT PM 공고 사이에 유의미한 차이 없이 0.4~0.5대에 몰리는 사례. 결합식을 곱으로 바꿔도
> 이 경우엔 두 후보의 도메인 점수 자체가 비슷해 순위가 크게 바뀌지 않는다 — 근본 원인은
> 결합식이 아니라 모델의 도메인 판별력 자체다. Phase 15에서 기본 모델을 `jhgan/ko-sroberta-
> multitask` → `snunlp/KR-SBERT-V40K-klueNLI-augSTS`로 교체해 실측 기준 약 3배 개선했지만
> (`docs/SPEC.md` §11-3-1), 완벽한 도메인 판별을 보장하지는 않는다 — job_text에 회사명 포함
> 등은 여전히 향후 검토 과제로 남긴다.

### 6-3-1. 상세 요건 최종검수 (`jobfind.py verify`)

`evaluate`로 추린 공고 목록은 여전히 목록 페이지 요약(제목·조건 태그)만 본 결과라, 실제
상세 자격요건과 다를 수 있다 — 예: 목록엔 "경력"이라고만 나오지만 상세엔 "유관 경력 5년
이상"이 명시된 경우. `verify`는 아직 검수하지 않은 공고마다 실제 상세 내용(원티드는 상세
API 텍스트, 사람인은 상세 페이지 이미지 — 본문이 이미지로 업로드돼 있어 텍스트로는 얻을
수 없음, §13-3 유사 한계이지만 원인이 다름)을 가져와 `profile.md`와 대조하고, `[검수]
PASS/CONCERN/UNKNOWN: <근거>` 한 줄을 블록에 남긴다. 자동으로 지우지 않는다 — AI 판단이
틀릴 수 있으므로 최종 제외 여부는 사용자가 `[X]` 마커로 직접 정한다. 이미 `[검수]`된
공고는 재실행해도 다시 확인하지 않아 비용이 중복되지 않는다.

### 6-4. 수동 추가 (`jobfind.py add <url>`)

사람인 공고 상세 URL 또는 원티드 공고 URL(`wanted.co.kr/wd/<id>`)을 입력하면 단건 조회 후
`jobs_all.txt`에 병합한다. 이미 있는 공고(ID 기준)는 건너뛴다.

### 6-5. 자소서 선택 및 보충 자료 (`jobfind.py select`)

`jobs_all.txt`의 공고 블록 마커를 `[자소서]`로 바꾸면(최대 4개), `select` 실행 시
`output/cover_letters/<공고ID>/materials/` 폴더가 생성된다. 사용자는 이 폴더에 공고
스크린샷(이미지)이나 `notes.md`(추가 메모)를 직접 넣어둘 수 있으며, 계획 단계에서 참고된다.
`notes.md`는 실제 자소서 문항(문항 제목·글자수 제한 등)을 반영할 수 있는 경로다 — 있는
경우 계획·작성 단계가 표준 구성 대신 이 내용을 최우선으로 따른다(Phase 18). `select` 실행
시 각 공고마다 이 파일 경로와 함께 채워두라는 안내를 콘솔에 출력하며, `[출처] 자소설닷컴`
공고이고 `[자소서문항]` 줄이 있으면 실제 문항 문구를 자소설닷컴에서 직접 확인해 옮겨
적으라는 안내가 추가된다(Phase 23) — 사람인·원티드는 여전히 지원서 제출 폼의 실제 문항을
자동으로 가져올 수 없고, 자소설닷컴도 문항 유무만 알려줄 뿐 문구 자체는 API에 없어
`notes.md` 수동 입력이 여전히 필요하다. 5개 이상 선택 시 경고를 출력한다.

### 6-6. 자소서 오케스트레이션 파이프라인 (`jobfind.py write`)

선택된 각 공고(최대 4개)에 대해 다음 순서로 실행한다. 각 단계는 독립된 AI provider 호출이라
이전 대화 맥락을 공유하지 않는다 (격리됨).

```
계획 수립 → 계획 평가 → (NEEDS_REVISION이면 계획 재작성)
  → 초안 작성 → 초안 평가 → (NEEDS_REVISION이면 초안 재작성 → 재평가, 최대 1회)
```

- 계획·작성 단계는 `profile.md`(사용자 이력)와 공고 정보를 참고한다.
- 계획 단계만 `materials/`의 이미지를 함께 참고한다 (계획 산출물이 텍스트로 흡수하므로
  이후 단계는 원본 이미지가 다시 필요하지 않음).
- 원티드 공고는 상세 API의 담당업무·자격요건·우대사항을 추가로 가져와 계획·작성·평가
  전 단계에 반영한다. 사람인 공고는 상세 본문이 자바스크립트 렌더링이라 이 보강이
  불가능한 상태다 (알려진 한계, `docs/history/PLAN_ARCHIVE.md` Phase 12 참고).
- 초안 평가가 `NEEDS_REVISION`이면 계획 재작성과 동일한 패턴으로 **최대 1회** 초안을
  다시 작성하고 재평가한다(Phase 17) — 무한 루프/비용 폭주를 막기 위해 계획 재작성과 같은
  1회 상한을 둔다. 재작성 후에도 `NEEDS_REVISION`이면 더 반복하지 않고 그 결과를 그대로
  사용자에게 제시한다. 계획·초안 재작성 모두 `docs/pipeline` 공통 스타일 원칙(약점은 전체
  문서에서 1회만 언급, 미확인 회사 정보는 직접인용 금지)을 시스템 프롬프트에 공유해,
  평가 라운드마다 서로 다른 지침을 내리는 문제를 없앴다(`docs/SPEC.md` §13-1 참고).
- 공고 상세 정보가 부족해도(사람인의 알려진 한계 등) 작성 단계는 초안 작성 자체를 거부하지
  않는다 — 실사용 중 일부 공고에서 초안 없이 "정보가 부족하다"는 안내만 반환되는 문제가
  확인되어, 항상 표준 구성으로라도 실제 초안을 작성하도록 프롬프트를 보강했다
  (`docs/history/PLAN_ARCHIVE.md` Phase 14 참고).
- 계획 수립 전, 지원 기업이 DART에 등록돼 있으면 기업 개황을 자동 조회해 공고 정보에
  얹는다 (G9, `docs/SPEC.md` §13-5). 계획 단계는 `claude_cli` provider에 한해 웹 검색·웹
  조회 도구도 함께 쓸 수 있어(G10, `docs/SPEC.md` §13-6), 회사 최근 뉴스·홈페이지까지
  스스로 찾아 계획에 반영할 수 있다.
- 결과는 `output/cover_letters/<공고ID>/{plan,plan_review,draft,draft_review}.md`에 저장한다.

### 6-6a. 자소서 작성 전략 (G14)

계획·계획재작성·계획평가·작성·작성재작성·초안평가 6개 시스템 프롬프트 전부가 공통 "작성
전략" 지식을 공유한다(`jobfind/pipeline/writing_strategy.py`) — 두괄식 구조, STAR(상황-
과제-행동-결과) 서술, 지원동기 구체성(다른 회사로 바꿔도 말이 되는 범용 문장 금지), 경험을
다른 직무·산업에 연결할 때 피상적 유사성이 아닌 실제 전이 가능한 역량으로 설명하기, 클리셰
회피, 약점 4단계 서술, 입사 후 포부의 단기/중기/장기 구조화. 평가 두 단계(계획평가/초안평가)
는 이 전략 위반을 실제 `NEEDS_REVISION` 판정 근거로 쓰도록 추가 지시를 받는다.

이 지식은 두 출처에서만 얻는다: (1) 공개적으로 발행된 자소서 작성법 콘텐츠(커리어 플랫폼
칼럼·HR 담당자 기고 등 — 특정 개인의 합격 자소서 원문이 아니라 그 자체로 누구나 보고
배우라고 공개된 일반 작성법), (2) 사용자 본인 소유의 과거 지원 자료 분석. **제3자 개인이
작성한 합격 자소서 원문(자소설닷컴·잡코리아 합격자소서 게시판 등)은 수집하지 않는다** —
열람 가능 여부와 무관하게 원저작자(실제 지원자 개인)의 저작권이 별도로 존재하고, 대부분
유료·회원제 서비스라 자동 수집이 이용약관에 저촉될 가능성이 크며, 실명 등 개인정보도
포함돼 있어 비상업적·공익적 목적이라는 사정으로 정당화되지 않는다는 판단이다(Phase 15
자소설닷컴 연동 보류 결정과 동일한 판단 기준, `docs/PLAN.md` Phase 21 참고).

### 6-7. AI Provider 선택 (`.env`의 `PROVIDER_*`)

계획/계획평가/작성/초안평가 역할마다 아래 중 하나를 선택한다.

| Provider | 방식 | 비용 |
|---|---|---|
| `claude_cli` | `claude -p` 헤드리스 호출 | 로그인된 세션 사용 (구독/한도에 따라 다름) |
| `api:anthropic` | Anthropic Messages API 직접 호출 | 호출당 과금 |
| `api:openai` | OpenAI Chat Completions API 직접 호출 | 호출당 과금 |

> **Codex CLI(`codex_cli`) 지원은 Phase 20에서 폐기했다.** 개발 환경에 Codex CLI가 설치돼
> 있지 않아 끝까지 실제 플래그로 검증하지 못한 채 남아 있었고(옛 OQ4), 실사용 필요성도
> 없어 `claude_cli`/`api:*` 두 경로로만 운영하기로 확정했다. 재도입하려면 `codex --help`로
> 실제 헤드리스 실행 규약부터 확인해야 한다.

### 6-7a. 지원 상태 추적 (G12, `[상태]` 마커)

`jobs_all.txt`의 블록에 `[상태] 지원함`처럼 자유 텍스트로 진행 상황을 적어둘 수 있다.
`collect` 실행마다 자동으로 스캔한다 — "탈락"만 `[X]`처럼 목록에서 제거되고
`output/archived_ids.txt`에 영구 기록되며(이후 재수집도 안 됨), 나머지 값(지원함/면접/
합격 등)은 목록에 그대로 남고 콘솔에 `[지원 현황] 지원함 3건, 면접 1건`처럼 집계만
출력된다. 상태 변경 이력(언제 바뀌었는지)은 추적하지 않는다.

### 6-7b. 복수 직무 묶음 공고 감지 (G13, `[공채후보]` 마커)

`collect`/`add`로 공고를 저장할 때 제목에 "공채/공개채용/부문별/직군별/직무별/전 부문/
전 직무/통합채용/N개 부문" 같은 신호가 있으면 블록에 `[공채후보]` 한 줄을 자동으로 남긴다
(자동 생성 필드라 `[상태]`처럼 사용자가 직접 적는 값은 아니다). 실제로 여러 직무를 분리해
보여주지는 않는다 — `select` 실행 시 이 마커가 있고 `[자소서]`로도 선택된 공고에 한해,
`materials/notes.md`에 실제 지원하려는 세부 직무를 적어두라는 안내를 추가로 출력한다
(기존 Phase 18의 notes.md 우선 반영 채널을 그대로 재사용).

> 직무 태그 개수만으로도 판별을 시도했으나, 실사용 데이터로 검증한 결과 사람인이 단일
> 직무 공고에도 유사 태그를 4~5개씩 붙이는 경우가 흔해(예: 영업 공고에 "솔루션기술영업,
> 영업, 영업기획, 판매, IT·통신기기판매") 오탐률이 높았다(검증 표본 9건 중 3건). 제목
> 패턴만으로 판별하도록 확정했다 (`docs/PLAN.md` Phase 19 참고).

### 6-8. 중복 방지

- 공고 ID에 소스 prefix를 붙여 관리한다: `saramin_XXXXX`, `wanted_XXXXX`.
- 실행 시 `jobs_all.txt`를 읽어 이미 수집된 ID는 결과에서 제외한다. `archived_ids.txt`에
  기록된 ID(탈락 처리된 공고, G12)도 동일하게 제외된다.
- 신규 공고만 `jobs_all.txt`에 추가한다.

### 6-9. 결과 파일 형식

파일 경로: `output/jobs_all.txt` (없으면 자동 생성, 있으면 append)

공고 1건의 형식과 마커 4종(`[ ]`/`[X]`/`[자소서]`/`[상태]`)의 의미는 `README.md`
"출력 파일 형식"과 `docs/SPEC.md`를 참고.

### 6-10. 로그

- 각 커맨드는 실행 시 콘솔에 처리 건수 요약을 출력한다.
- 예: `[2026-08-14 12:05] 조회: 85건 | X 처리: 2건 | 필터 통과: 12건 | 신규 저장: 8건`
- 오류 발생 시 오류 내용도 콘솔에 출력한다.
- `collect`는 콘솔 출력과 동일한 내용을 `output/run_log.txt`에도 한 줄씩 누적 기록한다.
  세 소스(사람인·원티드·자소설닷컴) 중 하나가 요청 자체 실패로 0건이 됐거나(오늘 신규
  공고가 실제로 없는 정상적인 0건과는 구분됨), 사람인이 페이지 상한(10페이지)에 도달해
  더 많은 공고가 있을 수 있는 경우 `[경고]` 태그를 붙여 강조한다.

## 7. 비기능 요구사항

| 항목 | 기준 |
|---|---|
| 실행 시간 (`collect`) | 세 소스 수집 포함 60초 이내 완료 — 단, 자소설닷컴은 신규 회사만
  상세조회하므로 이 기준은 평상시 실행 기준이며, 최초 도입 시 그 달 전체(400건 이상)를
  상세조회하는 1회성 실행은 예외로 더 걸릴 수 있다(실측 약 18초/200건, Phase 23) |
| 보안 | API 키는 `.env`에만 저장, 코드 하드코딩 금지. `profile.md`는 개인정보라 Git 제외 |
| 인코딩 | 모든 파일 입출력 UTF-8 |
| 격리 | 자소서 파이프라인의 각 AI 호출은 독립 실행되어 이전 단계의 대화 맥락을 공유하지 않는다 |
| 의존성 | `requests`, `python-dotenv`, `beautifulsoup4`, `sentence-transformers` 외
  표준 라이브러리만 사용 |

## 8. 데이터 흐름

```
[사람인]              [원티드]
    │ (스크래핑)            │ (API)
    ▼                        ▼
fetch_saramin_all()   fetch_wanted_all()
    └──────────┬───────────┘
               ▼
         dedup + 1차 필터(.env)
               ▼
        output/jobs_all.txt (collect)
               │
               ▼  evaluate
   HF 임베딩 관련성 랭킹 → 상위 top_n건만 유지
               │
               ▼  add (선택)
        수동 추가 공고 병합
               │
               ▼  select
   [자소서] 마커 스캔 → materials/ 폴더 준비
               │
               ▼  write
  공고별: 계획 → 계획평가 → (재작성) → 작성 → 초안평가
               ▼
  output/cover_letters/<공고ID>/{plan,plan_review,draft,draft_review}.md
```

## 9. 성공 기준

- `collect`~`evaluate` 실행 후 `jobs_all.txt`에 조건에 맞고 관련성 높은 순으로 정렬된 공고가
  올바른 형식으로 남는다.
- 같은 날 두 번 `collect`를 실행해도 공고가 중복 추가되지 않는다.
- `.env`의 조건을 바꾸면 다음 실행부터 바뀐 조건이 적용된다.
- `[자소서]`로 선택한 공고에 대해 `write` 실행 시 4개 산출물(plan/plan_review/draft/
  draft_review)이 모두 생성되고, 평가 단계가 실제로 구체적인 피드백을 낸다 (rubber-stamp
  아님 — Phase 12 실데이터 검증에서 확인됨).
- provider를 `claude_cli`에서 `api:anthropic` 등으로 바꿔도 동일한 파이프라인이 동작한다.
