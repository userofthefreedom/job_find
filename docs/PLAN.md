## 구현 전략

전체를 여러 Phase로 나눈다. Phase가 끝날 때마다 테스트를 실행하고 사용자 확인 후 다음 Phase로
진행한다.

Phase 1~4(v1)·8~16(v3 재설계 및 후속 피드백 반영)는 전부 완료됐다. 각 Phase의 구현 내용·
검증 로그·시행착오는 `docs/history/PLAN_ARCHIVE.md`에 전문 그대로 보존돼 있다 — 코드 동작
방식은 `docs/SPEC.md`가 최신 기준이므로, 과거 Phase 로그는 "왜 지금 이렇게 됐는지" 배경이
필요할 때만 참고한다.

**Phase 7(아래)은 2026-07-10에 세운 로드맵 초안의 마지막 남은 항목으로, 아직 구현에
착수하지 않았다.** 2026-08-14 세션에서 범위가 훨씬 크게 확장되며 Phase 8~15로 대체
착수했고, 2026-08-15엔 실사용 피드백으로 Phase 16(공고 최종검수)·Phase 5(안정성/신뢰성)·
Phase 6(필터 고도화)까지 이어서 완료됐다. Phase 7(지원 상태 추적)은 지금도 여전히 유효한
개선 후보다 — 작업 재개 시 지금 구조(`jobfind/` 패키지)에 맞게 다시 계획해야 한다.

## Phase 7 — 공고 관리: 지원 상태 추적 (예정)

**목표**: 기존 `[X]`(제거) 마커는 유지하고, 지원 상태(지원함/면접/합격/탈락)를 기록할 수 있게 확장

### 설계 결정 (2026-08-15, 사용자 확정)

- **마커 문법**: 기존 `[ ]`/`[X]`/`[자소서]` 마커는 그대로 두고, **새 줄 `[상태]`를 별도로
  추가**한다(예: `[상태] 지원함`) — 기존 마커 로직과 겹치지 않아 더 안전하다는 판단.
- **"탈락" 처리**: `[X]`처럼 `jobs_all.txt`에서 제거하고 별도 파일(`archived_ids.txt` 등)에
  영구 기록한다 — 목록이 깔끔하게 유지된다는 판단.

### 아직 남은 세부 설계

- "지원함/면접/합격"은 `jobs_all.txt`에 계속 남아 있어야 확인 가능 — 매 실행마다 스캔하되
  제거는 하지 않고 상태만 읽어 콘솔 요약에 반영(예: "지원함 3건, 면접 1건")하는 정도가
  적절해 보임
- 상태 변경 이력(언제 바뀌었는지)까지 추적할지는 범위 밖 — 단순 텍스트 파일 기반 원칙과
  충돌
- `[상태]` 값의 정확한 어휘(지원함/서류합격/면접/최종합격/탈락 등 세분화 여부)는 착수 시
  확정

### 작업 목록 (착수 시 위 세부 설계 확정 후 구체화)

- [ ] 상태 마커 파싱 함수 추가 (`storage.py`의 블록 파싱 재사용) — `[상태]` 줄 읽기/쓰기
- [ ] "탈락" 처리 — `[X]` 처리와 유사한 흐름으로 `jobs_all.txt`에서 제거 + `archived_ids.txt`
      기록
- [ ] 출력 형식에 `[상태]` 마커 반영
- [ ] `docs/SPEC.md` §4-5(마커 처리 명세)를 상태 마커까지 포괄하도록 확장
